2. **`solr/` ends up readable only by its owner (mode `0700`).** `mktemp -d` creates the stage directory with mode `0700`, and that directory gets renamed to `solr`. My test showed `drwx------ solr`. The old `mkdir -p solr` respected the umask. If Solr or anything else reads the tree as a different user, it will fail. Add `chmod 755 "$$stage"` (or `chmod u=rwx,go=rx`) after the `mktemp`.

1. **Nothing checks that Solr is stopped.** It's only mentioned in a comment. If Solr is running, the `mv solr …` succeeds and the process keeps writing to the backup's index, while `cp -a` has already copied a half-written index into the new tree. When upgrading, can solr be automatically stopped?

## CodeCompanion (Claude Code)

Yes, it can. The rule only runs when a Solr version upgrade is actually needed, so stopping Solr there is cheap. Starting it again afterwards is just as easy. I'd do it like this:

1. **If Solr is running under supervisor:** run `bin/supervisorctl stop solr` and confirm with the existing process check that it really stopped. Then do the install and run `bin/supervisorctl start solr`. If the install fails, the existing rollback puts the old `solr/` back, and the start brings the old version up again. Either way, Solr ends up running.
2. **If Solr is running but not under supervisor** (started by hand): keep failing with the current message. `solr/bin/solr stop` would work in theory, but the rule wouldn't know how to restart it with the same options. The supervisor config sets `SOLR_MODULES`, `solr.allowPaths` and others.
3. **If Solr is not running:** install and leave it stopped, as now.

Things to know before choosing this:

- **A plain `make` causes downtime.** `make` runs `all`, which includes Solr. A version bump would then restart Solr during a routine deploy, and Plone search would fail for the few seconds it's down. Today the build fails and someone has to stop Solr by hand, so the downtime is a deliberate step. Automatic stopping is more convenient but less explicit.
- **The first start of a new version takes longer**, because the core is loaded with the new JARs. If that start fails, `make` should report it clearly rather than end silently with Solr down. `supervisorctl start` gives a non-zero exit code in that case, so the build would fail.

I recommend automatic stop and start for the supervisor case only (option 1), and keeping the error for Solr started by hand. If you'd rather keep the downtime explicit, a middle ground is to make it opt-in with a variable such as `make SOLR_RESTART=1`.
